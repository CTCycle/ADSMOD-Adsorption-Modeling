# ADSMOD project status ledger

Last updated: 2026-11-09

This is the canonical current-state catalog for ADSMOD. It records validated
scope, meaningful limitations, open product decisions, evidence anchors, and
the smallest useful revalidation path. It is not a chronological QA journal.

## Baseline and branch status

The baseline source for this ledger is the `develop` implementation commit
`83c98fafe52cd4f12c6e9b1e3bf52b21e5692ed6`. It is the v3 architecture: Angular
client, one FastAPI backend, application settings in the selected database,
database connection settings in the independent data-root `database.json`, and
optional ML capabilities loaded in-process. Current source changes below reopen
the affected gates until their full validation scope is repeated.

The local refs at that implementation commit were not release-equivalent:

- `main` is `e8394e8`; `origin/main` is `64ee8ca`.
- In the local refs, `develop` is 274 commits ahead of and 7 commits behind
  `origin/main`.
- `origin/main` still contains the former React/Tauri-era client and launcher
  layout, while `develop` contains the current Angular/local-web line.
- The launcher update action intentionally targets a clean `main` checkout.
  Branch synchronization and release-baseline selection therefore remain
  follow-up work; this ledger describes `develop`, not `main`.

## Logging

The backend CLI filters successful routine access requests by default while
retaining failed requests and successful writes; `ADSMOD_LOG_LEVEL=DEBUG`
restores routine access diagnostics on the console. Focused access-policy tests
cover the normal and debug cases. The full Windows launcher lifecycle has not
been rerun for this change.

### Scientific accuracy audit

The 2026-11-07 audit (`85ee4c9`) did not establish scientific correctness. The
source fixes for `ADS-01`–`ADS-07` and `ADS-09` landed on 2026-11-08 and are
covered by unit and backend tests (`test_fitting_accuracy.py`,
`test_ml_accuracy.py`, `test_ml_contracts.py`, `test_data_processing.py`,
`test_fitting_sessions.py`): unweighted fits ignore uncertainties, explicit
bounds are never widened, fitted parameters on a bound warn, the input
fingerprint covers uptake uncertainty and duplicate policy, saved sessions are
flagged stale when their data changes, ML snapshots exclude multi-component
and non-Pa isotherms with reported counts, pressure/uptake pairs are trimmed
and subsampled together, ML R² uses dataset-level sufficient statistics, and
unit conversion fails closed. Still open: `ADS-08` grouped-holdout validation
(interpolation versus unseen-material benchmarks) and the real-dataset ML
benchmark; the 2026-10-22 ML lifecycle remains a small synthetic run. Fitting
and ML slices stay unrevalidated in the browser until `ADS-T2-05` and
`ADS-T4-02`/`ADS-T4-03` are rerun on the new code.

## Evidence rules

- `VALIDATED` always names the scope that was exercised; it does not mean
  production readiness, scientific correctness, or continuous provider uptime.
- Unit, lint, static, schema, or build results cannot alone prove a live browser,
  provider, hardware, or long-running workflow.
- A later source change lowers confidence until the affected slice is rerun.
- Keep active limitations here; move resolved findings into the compact decision
  table or the relevant concept document.
- Keep detailed run artifacts out of this ledger. Use repository tests, hosted
  URLs, canonical contracts, and only irreplaceable retained evidence.
